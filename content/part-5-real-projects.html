Interview trap: the order of assertEquals

TestNG: Assert.assertEquals(actual, expected). JUnit: assertEquals(expected, actual). The order is opposite. Mixing them up still passes or fails correctly, but the failure message will be confusing.

Data-driven test

Run the same test with many inputs. Great for checking many users, books or error cases.

Soft assertions

A normal assert stops the test at the first failure. SoftAssert keeps going and reports all failures at the end.

Run groups and in parallel: testng.xml

Pieces most good frameworks have

  • Config file for URLs per environment: mvn test -Denv=qa.
  • Endpoints class so paths are written once.
  • POJOs and a data factory to build test data.
  • Reports: Allure or ExtentReports.
  • Logging and CI: runs on every code change (Jenkins, GitHub Actions).
  • Independent tests that create and clean up their own data.

Cookies, files and waiting

Good to know
  • Environments: read System.getProperty("env", "qa") and load matching config.
  • Parallel runs: global RestAssured.* values are shared by every thread. Prefer specs.
  • GraphQL: it is a POST with a JSON body like {"query": "{ books { title } }"}. REST Assured can do that too.
  • Content-Type charset: REST Assured may add ; charset=ISO-8859-1. Switch off with EncoderConfig.encoderConfig().appendDefaultContentCharsetToContentTypeIfUndefined(false).

A good habit to say in the interview

"When a test fails, I first read the assertion message, then turn on log().ifValidationFails() to see the request and response. Most problems are a wrong URL, missing header, expired token or changed data."
